# BOOT → action → actual playback: code path and clocks

## True path map and confirmation owners

1. **BOOT release:** ESP `main/main.c:button_task` samples GPIO every 10 ms; `ptt_button_update` requires 25 ms stable input. `terminal_button` reports `device.capture/released` with device uptime. This is the debounced software release, not a physical-contact timestamp.
2. **Commit construction:** `main/speech.c:fetch_task` waits for the AFE frame. `ptt_capture.c:ptt_process` includes the last fetched frame at release, emits remaining PCM, then `input.commit`. There is no post-release VAD timeout on this path. A connection-start buffer holds up to 128,000 input samples; connection loss invalidates the hold.
3. **Device transmission:** `transport_pcm` Base64-encodes 320-sample/20 ms input chunks. `transport_send` serializes JSON into a 64-entry outbox, with 40 ms microphone enqueue limits and 100 ms non-microphone limits. `tx_task` serializes outgoing packets. USB writes can wait 250 ms per write; Wi-Fi send timeout is 500 ms. These are bounds, not measured usual delays.
4. **USB bridge:** `scripts/usb_bridge.py` uses a 20 ms serial read timeout, threaded serial I/O, one serial write lock, and WebSocket send/receive. `input.commit` is forwarded to Harness. Downlink PCM is decoded, split into 3,840-byte/80 ms source chunks, encoded again, written, then ACK-waited one chunk at a time. An ACK means device receipt/handling, not playback. Input and playback reports are read by the separate main loop.
5. **Harness commit / model:** `app.py:serve_socket` reads WebSocket JSON. `Harness.handle` acquires the session lock, rejects too-short input, submits `input_audio_buffer.commit`, records `input.committed`, and requests inference. If the prior response cancellation is not yet acknowledged, `_flush_manual_response` defers new inference. Outbound clients have 256-event queues; actual WebSocket writes run in sender tasks. Synchronous JSON persistence and provider sends still occur under the session lock.
6. **Same-turn final ASR:** `input_audio_buffer.committed` binds provider item ID to the original committed turn. `SpeechInputs` associates the final transcript by item/turn. Tool arguments may arrive first; `_perform_tool` waits up to 1.5 s on that turn's ASR event **outside the session lock**. Missing/invalid/superseded input does not dispatch a page write. This event-driven wait was already correct and was not shortened.
7. **Tool dispatch / page acceptance:** `_launch_tool` validates parameters, deduplicates call IDs and persists the call. Side effects share `mutation_lock`; read-only tools do not. `_perform_tool` rechecks turn/provider/response/page revision before `tool.request`. SDK `actionChain` serializes actions and returns cached acknowledgments for duplicates. New turn/session/transport guards invalidate only unfinished intent; actual completed results still reach Harness on the original live transport.
8. **Workshop pre-submit path:** Explicit kind/color calls `DemoController.command`: state GET → cancellation recheck → version-guarded command POST. Complex reference resolution: state GET → cancellation recheck → resolve POST → cancellation recheck → command POST using the resolved revision. The backend snapshots candidates under `RLock`, runs the decision outside the lock, then rechecks scene version. No speculative mutation or extra intent regex was added. The parent workshop patch owns runtime/version hardening and these controller changes.
9. **Acceptance versus simulation:** Backend `Workshop.command` deduplicates `request_id`, validates scene constraints, then either completes an immediate operation or starts a background job. `accepted:true/task_id` is not a physical-completion receipt. Worker preflight, motion, per-substep collision checks, pause/cancel events and MuJoCo/welding completion checks remain separate. `_finish` / terminal status records the physical-model result.
10. **First state / first visible frame:** HTTP state and SSE enter `WorkshopStateCache` (version/runtime/order guards), then `acceptState` coalesces `pendingRender`. `onState` is asynchronous and not awaited by tool acknowledgment. `demo.js:render` updates geometry/pose/UI; a later renderer frame displays it. SSE snapshots target 30 Hz when running and 350 ms when idle; HTTP fallback poll is 600 ms. Neither state acceptance nor a completed `onState` proves GPU presentation. No first-visible-frame metric was claimed here.
11. **Physical completion notification:** `demo.js:reportCompletion` sees a terminal snapshot after accepted tool acknowledgment, reports `task.update` with `source_call_id`, and retries unacknowledged reports no more often than 2.5 s. Harness validates accepted task/page identity and deduplicates before `task.completed/task.ack`. Only at a quiet boundary does `TaskUpdates` request result speech. The patch removes the additional 100 ms polling quantization, retaining the 500 ms guard and explicit audio drain requirement.
12. **Actually played sound:** Qwen `response.audio.delta` means generated bytes. Narration sends at most 0.75 s ahead in 0.1 s chunks and advances only on played samples. ESP stages 24→16 kHz converted samples into its ring; I2S DMA completion credits source samples only when a descriptor returns. `device.playback_started` records that DMA timestamp; `playback.progress` is normally reported by the 100 ms main loop. Browser reports use `AudioContext.currentTime` plus source `onended`, never bytes sent. Harness records heard text only after `done`, noninterrupted status, full played samples and a drain acknowledgment.

## Timing schema and clock alignment

Selected existing events carry `latency = {trace_id, turn, clock, origin, stage, elapsed_ms}`. `trace_id` is `session_id:turn`; call, response, task and provider item IDs remain separate joins. Manual origin is **Harness receipt of `input.commit`**, including waiting for its session lock, not the beginning of the spoken utterance. Text uses `input.text_received`; automatic VAD uses `speech_stopped_handled`.

Stages distinguish final transcript, tool dispatch start, tool-result persistence, task-result report, first generated audio, first audio dispatch, generation end, first positive played-sample **receipt**, and final drain **receipt**. `tool_result_recorded` can mean asynchronous acceptance. `task_result_reported` is the page's report of the terminal job, not an independently probed robot timestamp. No remote receipt is mislabeled as a local action time.

When older jobs are announced in a later user turn, `task_sources` follows the response through generation and playback, retaining each `task_id`, `source_call_id`, `source_turn` and original trace ID. Each source gets its own elapsed time when its origin remains in the bounded 64-turn history. Evicted origins retain IDs without inventing a duration. The top-level event's latency still represents its execution turn. Legacy `first_audio_ms` is preserved for UI compatibility, with `first_audio_kind=generated_at_harness` and `first_audio_origin`; for task result speech it measures from requesting the announcement, whereas task-source elapsed values measure from the original input.

ESP uptime, Python monotonic time, JavaScript `performance.now()` and wall timestamps have independent origins. **Never subtract them directly.** Device `button_release_to_play_ms` is meaningful only within the same device uptime epoch/response; the bridge's existing uptime-to-uptime delta requires no host clock subtraction. For a future full trace, retain epoch plus turn/response joins and either use within-process durations or an explicit RTT/clock-offset estimate with uncertainty. Browser presentation and acoustic latency remain unmeasured.
